## Start a new App

Two tables and twenty-one lines of TypeScript are an App you can list, search,
filter and edit.

<div class="tw-new">
<div>

```sql title="schema.sql"
create table customer (
  id serial primary key,
  name text not null,
  email text
);

create table invoice (
  id serial primary key,
  customer_id integer not null references customer (id),
  total numeric(10, 2) not null,
  paid boolean not null default false
);
```

```json title="mistri.json"
{
  "connections": [{
    "name": "billing",
    "url": "postgres://localhost/billing",
    "writable": true
  }]
}
```

</div>

```ts title="app.ts"
import { defineApp, listView } from '@mistriwork/mistri/app';

export default defineApp({
  id: 'billing',
  name: 'Billing',
  connection: 'billing',
  resources: {
    customer: { access: 'write' },
    invoice: { access: 'write' },
  },
  views: {
    invoices: listView('Invoices', 'invoice', {
      show: ['customer_id', 'total', 'paid'],
    }),
    customers: listView('Customers', 'customer', {
      show: ['name', 'email'],
    }),
  },
  nav: ['invoices', 'customers'],
  home: 'invoices',
});
```

</div>

```sh title="Terminal"
npm init -y && npm pkg set type=module && npm install @mistriwork/mistri typescript
createdb billing
npx @mistriwork/mistri migrate diff init --app .   # writes migrations/V1__init.sql from schema.sql
npx @mistriwork/mistri migrate up --app .          # applies it, then checks the App against it
npx @mistriwork/mistri dev                         # serves it, and reloads on every save
```

You read the first migration before it runs; the next comes the same way when
you change `schema.sql`. No front end to write, no API to wire, no build step
to serve. Starting with nothing, `npm create mistri billing` makes a starter App
with a SQLite database of its own; with a database you have, mistri drafts the
App from it. [Get started](/docs/getting-started/)

## The DSL: a few lines is a screen

Lintel, the flagship sample, runs a property company's three Denver buildings:
leases, a rent ledger, repairs, a storeroom, a public listings site and a
resident portal. It is about 1,500 lines of TypeScript, commands and jobs
included, not counting blank lines, comments or tests, checked against the
database before anyone opens a page. Three cuts from it:

## Hooks: yours to change

When a default is not enough, each layer has a hook, and what you write is
still checked against the database. Ladle, a cooking school, draws its door
list as a page of its own:

```tsx title="examples/apps/ladle/pages/check-in.page.tsx"
const page = definePage({
  label: 'Check-in',
  reads: ['class_session', 'booking'],
  commands: ['checkIn'],
  params: ['class'],
  component: CheckIn,
});
```

The page reads only what it declares, under the reader's grants, writes only
through its command, and draws the App's own blocks beside its React.

## The agent loop

Coding agents build Apps with mistri: a typed DSL that keeps an App short, a
check that answers precisely when it is wrong, and MCP to see what the running
App did. Install the skill, give the agent a brief, and it works against the
same checks you would.

<div class="tw-new">

<ul class="tw-ux tw-ux-list not-content">
  <li><strong>The skill where your agent reads it.</strong> <code>{'mistri agent init'}</code> installs it for Claude Code, Codex, Cursor and GitHub Copilot. <a href="/docs/build-with-an-agent/">Build with a coding agent</a></li>
  <li><strong>The schema in its context.</strong> <code>{'mistri schema --brief'}</code> prints one line per table, with keys, references and allowed values.</li>
  <li><strong>Wrong fails before a page opens.</strong> <code>{'mistri check'}</code> typechecks the App against the generated schema types and validates it against the database: a stable code, the file, and the fix, as lines or JSON. <a href="/docs/check-codes/">Check codes</a></li>
  <li><strong>It sees what it did.</strong> <code>{'--dev'}</code> records every request's SQL, each command's input and refusal cause, logs, N+1 and slow statements and page vitals, and <code>{'mistri observe --mcp'}</code> hands them to the agent as tools; <code>{'mistri shot'}</code> draws the App's pages as PNG files. <a href="/docs/observe/">Observe</a></li>
</ul>

<div>

```shellsession title="Terminal" wrap
$ npx @mistriwork/mistri agent init
$ npx @mistriwork/mistri schema --brief
…
customer(id* int, name text, email text?)
invoice(id* int, customer_id int → customer, total num, paid bool)
$ npx @mistriwork/mistri check --app . --brief
unknown-column app.ts view "invoices": This view's show cannot be resolved on "invoice": "amount" ("amount" is not a column on invoice.). — fix: use a column the table has (the message names the nearest; mistri schema --brief lists them)
```

</div>
</div>

An App's own reads and commands reach an agent as MCP tools too, under a scoped
token and the same grants as its screens. In production the same traces go to
your collector over OpenTelemetry.
